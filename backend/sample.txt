Database Management Systems

A Database Management System (DBMS) is software that provides an organized mechanism for storing, managing, retrieving, and protecting data. A DBMS allows users and applications to interact with databases without needing to understand how data is physically stored. Common responsibilities of a DBMS include data definition, data manipulation, transaction management, concurrency control, security, backup, and recovery. Database systems are widely used in banking, healthcare, education, e-commerce, transportation, and enterprise applications.

A database schema describes the logical structure of a database. It defines tables, attributes, relationships, constraints, and other database objects. A well-designed schema reduces redundancy and improves data consistency. The relational model represents information using relations, commonly implemented as tables. Each table contains rows representing records and columns representing attributes. A primary key uniquely identifies each row in a relation, while foreign keys establish relationships between related tables.

Database normalization is a systematic technique for organizing relational database tables to reduce redundancy and improve data integrity. Without normalization, the same information may be stored repeatedly in multiple rows. Repetition can lead to update anomalies, insertion anomalies, and deletion anomalies. Normalization divides large relations into smaller related relations and establishes appropriate relationships between them. The objective is to ensure that each fact is stored in an appropriate location and that dependencies between attributes are correctly represented.

First Normal Form, or 1NF, requires that every attribute contain atomic values and that repeating groups are eliminated. A relation should have a well-defined structure where each cell contains a single value. For example, storing several phone numbers in one attribute violates the principle of atomicity. A normalized design would represent the phone numbers in a separate relation or in multiple appropriate rows. First Normal Form provides the foundation for further normalization.

Second Normal Form, or 2NF, builds on First Normal Form. A relation must first satisfy 1NF and then every non-key attribute must depend on the entire primary key. This requirement is particularly important when a relation has a composite primary key. Partial dependency occurs when a non-key attribute depends only on part of a composite key. Such dependencies can cause redundancy and anomalies. Decomposing the relation can remove partial dependencies and produce a more consistent database design.

Third Normal Form, or 3NF, builds on Second Normal Form. A relation satisfies 3NF when it has no undesirable transitive dependencies between non-key attributes. A transitive dependency occurs when one non-key attribute depends on another non-key attribute rather than directly on the primary key. Removing transitive dependencies helps ensure that each non-key attribute describes the entity identified by the key. Third Normal Form is widely used in practical relational database design.

Boyce-Codd Normal Form, or BCNF, is a stronger version of Third Normal Form. A relation is in BCNF when every determinant is a candidate key. Some relations that satisfy 3NF may still contain redundancy caused by functional dependencies involving overlapping candidate keys. BCNF addresses these cases by requiring stronger dependency conditions. Although BCNF can improve database consistency, decomposition into BCNF relations may sometimes affect dependency preservation.

Functional dependencies are an important concept in relational database theory. A functional dependency describes a relationship in which the value of one attribute or set of attributes determines another attribute. If attribute X determines attribute Y, it can be written as X determines Y. Functional dependencies are used to identify candidate keys, analyze redundancy, and determine appropriate normal forms. They are also useful when reasoning about lossless decomposition and dependency preservation.

Database decomposition is the process of dividing a relation into two or more smaller relations. A good decomposition should ideally be lossless, meaning that joining the decomposed relations reconstructs the original relation without introducing incorrect tuples. Dependency preservation is another important property. A decomposition is dependency preserving if the original functional dependencies can be enforced without requiring joins of the decomposed relations. These properties are important when evaluating database schemas.

Database indexing is a technique used to improve the speed of data retrieval. An index is an additional data structure that allows a database engine to locate records more efficiently. Without an appropriate index, the database may need to scan a large number of rows. Common indexing structures include B-tree indexes, hash indexes, and specialized indexes. The choice of index depends on the query workload, data distribution, and operations performed on the database.

A B-tree index is commonly used for equality and range queries. It maintains keys in an ordered structure that allows efficient searching, insertion, and deletion. Database systems can use B-tree indexes to accelerate queries involving comparisons, sorting, and ranges. However, indexes also introduce storage overhead and can slow down insert and update operations because the index must be maintained whenever the underlying data changes.

Transactions provide a mechanism for executing a group of database operations as a single logical unit. Transactions are commonly described using the ACID properties: atomicity, consistency, isolation, and durability. Atomicity ensures that a transaction is completed completely or not at all. Consistency ensures that database constraints remain satisfied. Isolation controls the interaction between concurrent transactions. Durability ensures that committed changes survive failures.

Concurrency control is necessary when multiple users or processes access the same database simultaneously. Without appropriate concurrency control, problems such as lost updates, dirty reads, non-repeatable reads, and phantom reads may occur. Database management systems use mechanisms such as locks, timestamps, and multiversion concurrency control to manage concurrent operations. The selected strategy affects consistency, performance, and transaction throughput.

Query optimization is the process of selecting an efficient execution plan for a database query. A database optimizer considers available indexes, join methods, table statistics, filtering conditions, and estimated costs. Different execution plans can produce the same logical result but have significantly different execution times. Query optimization is therefore important for database performance, particularly when tables contain large numbers of records.

Vector databases extend traditional database systems by supporting storage and similarity search over high-dimensional vectors. A vector is a numerical representation of information such as text, images, or audio. Embedding models convert unstructured information into vectors that capture semantic characteristics. Similarity search can then identify vectors that are close to a query vector according to a distance metric such as cosine distance.

Retrieval-Augmented Generation, or RAG, combines information retrieval with language generation. A RAG system first receives a user query and converts it into a vector representation. The vector database then searches for chunks that are semantically similar to the query. The retrieved chunks are provided as context to a language model, which generates an answer grounded in the retrieved information. This approach can reduce the dependence on information stored only in the model's parameters.

An explainable vector database extends this architecture by providing evidence about why particular chunks were retrieved. Semantic similarity is one important signal, but other evidence can include keyword overlap, metadata relevance, ranking position, score margins, and document structure. For example, a chunk may rank highly because its embedding is very similar to the query and because it contains important concepts explicitly mentioned by the user.

Explainability should be based on measurable retrieval evidence rather than unsupported claims. An explanation engine can store individual evidence signals and their contribution to the final retrieval score. It can also identify the terms or concepts that overlap between the query and retrieved chunk. The system can compare the highest-ranked result with lower-ranked results to determine why one chunk was preferred over another.

A database management framework for explainable RAG therefore requires more than a vector similarity search. It requires a relational schema for documents, chunks, embeddings, queries, retrieval results, explanations, and performance logs. Constraints maintain data integrity, indexes improve query performance, vector indexes accelerate similarity search, and transaction management ensures that related records are stored consistently.

Performance evaluation is another important component of such a framework. Retrieval quality can be measured using metrics such as Precision at K, Recall at K, Mean Reciprocal Rank, and Normalized Discounted Cumulative Gain. System performance can be evaluated using embedding generation time, database retrieval latency, explanation generation time, and total request latency. Comparing these measurements across different chunk sizes and retrieval configurations helps determine the most effective system design.
